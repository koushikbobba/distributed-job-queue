STAGE 01

Ingestion & Idempotency

Client issues POST /api/jobs/. The API checks JWT validity, evaluates sliding-window rate limits (10 submissions/min), hashes the request payload with SHA-256, and checks PostgreSQL for cached responses. Duplicate requests return cached responses instantly without creating duplicate background tasks.

Guarantees: Zero duplicate execution
STAGE 02

Dual-Write Safety & Outbox

Inside an ACID transaction, the Job and an OutboxMessage are saved simultaneously. Django's transaction.on_commit() hook dispatches the job to Redis only after PostgreSQL commits to disk, eliminating the post-commit race condition where workers query uncommitted rows.

Pattern: Transactional Outbox + on_commit
STAGE 03

Worker Lock & Execution

Celery workers perform priority blocking pops (BRPOP). Before execution, workers acquire a Redis distributed lock (SETNX with TTL). Handlers execute business logic, record immutable audit rows in JobExecution, handle retries with jitter, and release the lock via atomic Lua script.

Safety: Atomic Lua Lock Release

Strict state transition validation preventing illegal mutations or corrupt status jumps.

Executive Engineering Summary

What is this project and what problem does it solve?

In conventional synchronous web applications, when an end-user triggers a computationally heavy operation (such as compiling an annual PDF tax report, processing bulk datasets, or dispatching 10,000 marketing emails), the web server thread executes that task directly within the HTTP request-response cycle.

This synchronous design introduces severe production vulnerabilities:

1. HTTP Gateway Timeouts (504)

AWS Application Load Balancers, NGINX reverse proxies, and browsers terminate connections that exceed 30–60 seconds, dropping the user's connection while the server continues working in vain.

2. Web Worker Thread Starvation

Gunicorn or Uvicorn worker threads blocked on long-running tasks cannot accept incoming requests from other users, causing complete application unresponsiveness.

3. Accidental Duplicate Execution

When network packets drop, frontend apps or automated webhooks retry the HTTP request, causing non-idempotent operations (such as charging credit cards) to run twice.

4. Worker Crash Message Loss

Standard task queues that acknowledge messages before execution immediately lose jobs forever if the worker process suffers an Out-Of-Memory (OOM) kill or power loss.

The Solution: This project implements an enterprise-grade Distributed Task Queue & Background Processing Platform. It decouples synchronous ingestion from execution. Incoming requests receive an immediate HTTP 202 Accepted response with a job_id in under 10 milliseconds, delegating background execution to horizontally scalable Celery workers coordinated by Redis and PostgreSQL.

5 Key Distributed Systems Challenges Solved

1. The Post-Commit Message Dispatch Race Condition

The Bug: If an API dispatches a task to Celery inside an uncommitted database transaction, message transmission over Redis takes <1ms. A fast worker pops the task from Redis and queries PostgreSQL (Job.objects.get(id=job_id)) before the web server's transaction has committed, immediately crashing with Job.DoesNotExist.

The Fix: We wrapped Celery publishing inside Django's transaction.on_commit() hook combined with a persistent OutboxMessage table. The task enters Redis strictly after PostgreSQL confirms the commit has hit disk.

2. Mutual Exclusion via Redis Distributed Locking

The Bug: Network retries or duplicate message deliveries can cause two workers to execute the same job simultaneously. Furthermore, if a worker's lock expires while it is still working, another worker grabs the lock. If the first worker finishes and blindly executes DEL lock:job:uuid, it deletes the second worker's active lock!

The Fix: We acquire locks via SET key token NX PX 120000 and release locks via an atomic Lua script verifying that the token in Redis matches the worker's unique UUID token before deletion.

3. Thundering Herd Storms & Exponential Backoff with Jitter

The Bug: If an external service or database suffers a temporary network glitch, hundreds of failing tasks retrying at identical exponential intervals (e.g. exactly 2s, 4s, 8s) will hit the recovering service at the exact same second, crashing it repeatedly.

The Fix: We calculate retries using Full Random Jitter: delay = random.uniform(0, min(300, 2^retry_count * base_delay)), dispersing retry traffic uniformly across the timeline.

4. Worker Crash Recovery (At-Least-Once Delivery)

The Bug: Default Celery acknowledges messages when received (acks_late=False). If a container is terminated mid-task, the job disappears without a trace.

The Fix: We configure task_acks_late = True and task_reject_on_worker_lost = True. If a worker process dies, Redis re-queues the message to another healthy worker, and a periodic Celery Beat reaper sweeps jobs stuck in PROCESSING.

5. Multi-Tenant Row-Level Isolation

The Bug: In multi-tenant platforms, attackers attempt ID enumeration attacks (guessing /api/jobs/1, /api/jobs/2) to view other tenants' sensitive task outputs.

The Fix: We enforce UUIDv4 primary keys and override DRF's get_queryset() with Job.objects.filter(user=request.user). Guessing another user's UUID returns HTTP 404 Not Found instead of 403 Forbidden, hiding resource existence entirely.
